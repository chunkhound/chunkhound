ChunkHound CI/CD Architecture

Continuous public PyPI alphas from successful main builds, with one shared release implementation and unchanged stable-release behavior.

Status: agreed design; implementation pending.

Agreed decisions

Production PyPI

Keep using public alpha versions as the testing surface. No TestPyPI.

Next available alpha

Each successful main build gets the next available alpha tag. Numbers reflect allocation order, not source commit order.

Tag is authoritative

The explicitly requested, immutable tag determines the release version and source commit. Never let Git choose among tags.

Simple recovery

Use existing manual Actions reruns and PyPI skip-existing. No automatic publication retries or special storage system.

Stable unchanged means unchanged behavior. Stable workflow code and shared helpers may be refactored, and OIDC may be reconfigured. Preserve the stable release contract—not the exact file contents.

End-to-end flow

Push to protected main
  → ci.yml validates the exact commit
      ├─ Documentation deployment (independent path)
      └─ prepare-alpha: create/reuse tag for github.sha using GITHUB_TOKEN
           → release-alpha: directly call release-packages.yml
                → build and validate distributions
                → publish chunkhound-native first
                → publish chunkhound second

Manual alpha/beta/RC tag → release-rc.yml wrapper → release-packages.yml
Published GitHub Release → release.yml wrapper   → release-packages.yml

No GitHub App is required. The automatic tag push does not need to trigger another workflow: CI calls the reusable workflow directly.

Alpha allocation

A reviewed file declares the intended next release line:

# .github/release-channel.toml
[alpha]
base_version = "6.2.0"

Inspect remote tags and select the next unused number:

Existing: v6.2.0a1, v6.2.0a2
Next:     v6.2.0a3

The configuration guides tag creation only. Once created, the tag is the source of truth. Tag the CI-tested github.sha, not a moving main tip.

  • Allocation order is intentional: an older commit that completes CI later may receive a higher alpha number. No commit-order queue is required.
  • Collision-safe creation: fetch tags, push without force, and refetch/retry if another build claimed the same number.
  • Idempotent reruns: reuse the same build's existing tag. Simultaneous reruns must not create multiple release identities.
  • Preserve main builds: the current shared CI concurrency group can replace pending runs even with cancel-in-progress: false. Allow independent main runs or another non-dropping mechanism. Coordinate Pages deployment separately.

Update the base version through a reviewed PR when moving to the next intended release line. Within one base, alphas sort below beta, RC, and stable versions; testers can install a specific alpha by its exact version.

Explicit release contract

# release-packages.yml
on:
  workflow_call:
    inputs:
      release_tag:
        required: true
        type: string
      source_sha:
        required: true
        type: string
  1. Validate the release tag and verify it points to source_sha.
  2. Check out that source with full history.
  3. Strip the leading v once to obtain the package version.
  4. Pass that exact version to both builds and verify the resulting metadata.

Override Hatch VCS version discovery during the main build:

- name: Build main distributions
  env:
    SETUPTOOLS_SCM_PRETEND_VERSION: ${{ needs.prepare.outputs.version }}
  run: uv build

The native build receives the same version through the Cargo patching logic:

Requested tag: v6.2.0a43
Main version:  6.2.0a43
Cargo version: 6.2.0-a43
Native wheel:  6.2.0a43
Do not use caller event context to select the version. A reusable workflow called from CI still sees the main push. Refactor native-wheel actions, version gates, and alerts to accept the explicit tag/version instead of inferring it from GITHUB_REF_NAME. Multiple tags may point to one SHA; the requested tag always wins.

Validate main and native artifact versions, the embedded main version, and the version retained when rebuilding the final sdist. Protect release tags against moving or overwriting.

Stable-release behavior contract

Share code where useful, while preserving:

  • The published-GitHub-Release trigger.
  • Main/native versions matching the requested tag.
  • The existing distribution types and supported platform matrix.
  • Existing stable dependency semantics.
  • Validation gates and native-first publication.
  • Equivalent approval controls, failure alerts, and manual rerun behavior.

Regression checks should cover this contract, including multiple tags on the same commit. OIDC configuration and implementation may change; externally visible stable behavior must not.

Permissions and publishing setup

  • prepare-alpha uses GITHUB_TOKEN with job-scoped contents: write. No App secret or PAT.
  • Tag rules must allow Actions to create alpha tags and alpha-build/** identity tags while protecting both against updates/deletion and retaining stable-tag creation controls. Identity tags point to metadata blobs and do not affect version discovery.
  • Release callers grant required contents: read, id-token: write, and issues: write; called jobs narrow permissions.
  • Configure PyPI Trusted Publishers for release-packages.yml, which is identified by the OIDC job_workflow_ref, with each matching environment: pypi, pypi-alpha, pypi-native, or pypi-alpha-native on the appropriate project. Old caller-only entries do not authorize these publishing jobs.
  • Alpha uploads require no manual approval. Separate alpha environments can preserve stable approval controls.

Artifact validation and native pairing

The shared release workflow preserves distribution builds, clean-install checks, artifact gates, and native failure alerts. Native publication must succeed before the main package is published.

The proposed alpha dependency contract is:

chunkhound==6.2.0a43
Requires-Dist: chunkhound-native == 6.2.0a43

Preserve this alpha pin in both wheels and the final sdist; verify a wheel rebuilt from the sdist retains it. Do not silently change stable dependency semantics.

CI job guard

prepare-alpha:
  needs: [tests, rust-checks, site-build-validation,
          watchman-rollout-gate, native-wheel-smoke-arm64,
          old-linux-wheel-smoke, native-dev-macos]
  if: github.event_name == 'push' && github.ref == 'refs/heads/main'
  permissions:
    contents: write
  # Create/reuse tag; output release_tag and source_sha.

release-alpha:
  needs: prepare-alpha
  permissions:
    contents: read
    id-token: write
    issues: write
  uses: ./.github/workflows/release-packages.yml
  with:
    release_tag: ${{ needs.prepare-alpha.outputs.release_tag }}
    source_sha: ${{ needs.prepare-alpha.outputs.source_sha }}

Failed validation skips tagging. PR, merge-queue, and manual CI runs do not allocate alphas. Documentation deployment failures do not block package releases.

Failures: keep the existing manual recovery

FailureResponse
CI validation failsNo tag or publication.
Tag creation failsFix and manually rerun; reuse a previously created tag.
Native build, validation, or upload failsMain publication stays blocked. Existing alert and manual failed-job reruns apply.
Main upload fails after native succeedsManually rerun failed publication jobs with existing skip-existing.
No new recovery system. Use existing Actions artifacts and manual reruns. Prefer rerunning failed publication jobs, which normally reuse built artifacts. A full workflow rerun may rebuild and overwrite Actions artifacts, as today. No automatic publication retry, checksum registry, or special storage is added.

Accepted limitation: after a full rebuild of a partially published version, PyPI may retain earlier files while missing files come from the rebuild. This is not a blocker for the first continuous-alpha step.

Implementation checklist

  1. Add the tracked alpha base-version file.
  2. Add CI preparation/direct release-call jobs with collision-safe allocation and idempotent reruns.
  3. Ensure main concurrency does not discard builds; coordinate Pages independently.
  4. Extract shared release logic; make stable/RC wrappers thin callers while preserving stable behavior.
  5. Pass explicit tag/version/SHA inputs and verify artifact versions.
  6. Configure release/identity tag protections, reusable-workflow OIDC trust, and approval environments.
  7. Validate alpha native pairing through wheels and sdist rebuilds; retain stable dependency semantics.
  8. Document channel rules and existing manual recovery. Add no automatic publication retries or special storage.
