ChunkHound MCP Area Analysis

Updated 2026-10-29 from a direct read of the ChunkHound code and the MCP SDK 2.3.0 source.

Key findings
  • Three front ends, one tool core: the daemon (hand-written JSON-RPC, no SDK), the SDK stdio server, and the SDK HTTP server. The default chunkhound mcp uses the daemon — the one path the SDK never touches, so SDK 2.x features only reach the other two.
  • Everything advertises an old protocol today. The daemon and stdio fallback hardcode 2024-11-05; the installed SDK (mcp 1.16.0) tops out at 2025-06-18.
  • Clients differ: Claude Code speaks 2026-07-28 when offered, with strict reply validation; Pi only speaks the legacy handshake (2025-11-25).
  • Target version is an open decision between 2025-11-25 and 2026-07-28. The latter cuts Pi off the default daemon path; the former has no cutover.
  • The daemon serializes one request at a time per client, with no progress, cancellation, or streaming — all of which SDK 2.3.0 provides.

Data flow per path

  • A. Default (daemon): most stdio clients (Claude Code, Pi, pi-mcp-adapter) with no flags. client → ClientProxy → IPC (Unix socket; TCP on Windows) → ChunkHoundDaemon._dispatch_mcp → handle_tool_call. The proxy is a dumb frame relay (token-authenticated via the lock file); DaemonDiscovery spawns the daemon if none is running. One daemon per project, exits after the last client disconnects.
  • B. Direct stdio (SDK, --no-daemon): used for --no-daemon, --stdio, CHUNKHOUND_DAEMON_MODE=false, read-only, or the chunkhound-mcp script. Each client gets its own process: client → StdioMCPServer → SDK Server → handle_tool_call. N clients = N SDK servers = N DuckDB connections.
  • C. HTTP (SDK): one process serves all HTTP clients. client → Starlette (bearer-auth /mcp, unauthenticated /health) → StreamableHTTPSessionManager(stateless=False) → SDK Server → handle_tool_call. Never uses the daemon.

Routing rules (verified in code)

  • --transport http wins over everything; --stdio is ignored there (with a warning).
  • No-daemon triggers on --no-daemon, --stdio, CHUNKHOUND_DAEMON_MODE=false, or database.read_only. Otherwise the proxy/daemon path runs.
  • Resolved: chunkhound mcp stdio does not select stdio mode — stdio parses as the positional path, so it takes the daemon path with project_dir = <cwd>/stdio. Fixture tests and the benchmark script exercise the daemon, not the SDK stdio server.

4. Leveraging the SDK server on the daemon path

Why the daemon path misses the SDK today

  • The daemon builds no SDK Server (self.server is None; _register_tools is a no-op). Its docstring says it works "without depending on the MCP SDK" so it can import independently.
  • The proxy and daemon speak framed JSON-RPC over IPC, not an SDK stream pair. SDK features that need a live stream (progress, notifications) have nowhere to go.
  • Dispatch is serial per client: _handle_client awaits _dispatch_mcp before reading the next frame. A long code_research call blocks that client's other requests, and a cancellation could not be read until the call ends.
  • All SDK-side value (discover, resultType, validation, cache_hints, middleware, OTel, progress, subscriptions/listen) is unreachable unless re-implemented by hand.
  • Re-implementing the minimum by hand (about 30 lines plus the pure helper classify_inbound_request) is cheap, but it leaves progress, cancellation, concurrency, and middleware out, and leaves two protocol implementations to keep in step.

Data flow for one message (Option B)

Client → proxy (parses the line, does nothing else) → IPC frame → daemon unpacks it into a typed SessionMessage on that client's in-memory stream. That client's run() picks its era from the first request, handles handshake/discovery/validation, and calls handle_tool_call — same shared core and DB writer as every other path. The reply retraces the same hops back to stdout. On disconnect, the stream closes, run() exits, and its in-flight handlers are cancelled (source-verified, not yet run).

What changes compared with today (Option B)

  • Daemon: loses the hand-rolled dispatcher and hardcoded 2024-11-05; gains an SDK session per connection with real cancellation/progress.
  • Proxy: unchanged relay, no SDK import.
  • New: an IPC-frame↔SessionMessage adapter and an HTTP adapter in the daemon; no registered SDK lifespan (run() would re-enter it per connection).
  • Unchanged: --no-daemon/--stdio/read-only routing, the shared tool core, the single DuckDB writer.

Option C: SDK Server in each proxy, daemon as a tool backend

Status: candidate, not decided — alternative to Option B, a spike decides between them. Each proxy hosts its own SDK server (own era negotiation) and calls the daemon through a small internal RPC (list_tools, call_tool) that needs its own versioning; the daemon stops speaking MCP and becomes a plain tool backend owning the DB writer. Needs SDK 2.x in the proxy for 2026-07-28 (mcp>=1.24.0,<2 suffices for 2025-11-25-only). Not verified: SDK import cost per proxy, and the stdio cancellation signal in 2026-07-28.

Data flow for one message (Option C)

Client → the SDK Server inside that proxy handles the protocol (handshake or discover, negotiation, validation, response fields). It then calls the daemon over the existing register/auth IPC via the internal RPC (list_tools/call_tool, tagged with a request ID; DaemonDiscovery spawns the daemon if needed). The daemon runs each request as its own task, calling handle_tool_call against the same shared core and DB writer as every other path, and reports progress as frames carrying the request ID. The result frame returns to the proxy, which writes it to stdout in the client's wire format. On disconnect, the daemon cancels that client's in-flight tasks (proxy's orphan watchdog unchanged).

What changes compared with today (Option C)

  • Daemon: loses the hand-rolled dispatcher and hardcoded 2024-11-05; gains per-request tasks, a write lock, cancellation, and progress frames.
  • Proxy: becomes a full SDK server whose handlers call the daemon, instead of forwarding raw lines.
  • Unchanged: HTTP path, --no-daemon/--stdio/read-only routing, the shared tool core, the single DuckDB writer.
  • Risks to check first: SDK cold-start per proxy, the stdio cancellation signal in 2026-07-28, and a version field on the internal RPC so mismatched proxy/daemon versions fail clearly.

Why the design keeps a shared tool core

  • The core (common.handle_tool_call, tools.execute_tool, TOOL_REGISTRY) is the one definition of the 5 tools: argument validation, execution, and error shaping. It already exists and is not new to either option.
  • Three callers need it: the daemon, StdioMCPServer (--no-daemon), and HttpMCPServer. Without it each would carry its own copy and the paths would drift apart.
  • It keeps the daemon protocol-free. The daemon only calls into the core and never builds MCP responses.
  • It is why the tool-wiring change matters: the SDK handlers in the proxy and in StdioMCPServer should call the same bound methods.

The --no-daemon flow (also --stdio, read-only, CHUNKHOUND_DAEMON_MODE=false)

  • No proxy, no daemon, no IPC. The SDK Server and the tool core run in the same process the client spawned.
  • Neither option changes this path. It already has a live SDK server, so it gets the SDK upgrade directly.
  • Each client gets its own process and its own DuckDB connection. Two clients with writers on the same database conflict. This is the reason the daemon exists. Read-only mode avoids the conflict, which is why it is forced onto this path.

5. Rust integration options for the MCP layer

This is a separate axis from section 4. Section 4 asks where the SDK session host runs (daemon vs. proxy), using the Python mcp SDK either way. This section asks how much of the stack moves to Rust if the official Rust SDK (rmcp, modelcontextprotocol/rust-sdk) is used instead.

Today's baseline (unchanged by this section): Rust (chunkhound_native) only does indexing — scanning, diffing, DuckDB writes, HNSW maintenance, and embedding calls for OpenAI/Azure/VoyageAI. It is a library loaded into the Python process (a PyO3 extension module), never the other way around. Python always initiates; when Rust needs Python (parsing, non-native embedding providers) it briefly re-acquires the GIL and calls a plain blocking Python function. The query/serving path (search, code_research, fetchurl, daemon_status, websearch) has zero Rust involvement today — it runs entirely on Python's own duckdb bindings and the Python tool core (mcp_server/tools.py), which is also what the CLI commands call directly.

A full rewrite ladder has five points (protocol only → +daemon → +daemon+proxy → +daemon+proxy+search → full tool-call revision). The +daemon and +daemon+proxy stops pay the heaviest architectural cost on the ladder — flipping process ownership to Rust, which forces embedding or sidecar-ing a full Python interpreter (the harder, reversed direction from today's library-call pattern) — while leaving 100% of every request's real work in Python, so they are not listed as standalone options below. Only the realistic stopping points are shown: the lowest-effort way to adopt the Rust SDK, and the best mid- and high-effort options.
