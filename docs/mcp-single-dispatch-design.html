ChunkHound MCP — Single-Dispatch-Point Design

Extends Option B (mcp-daemon-option-b-plan.html) with one additional constraint: there is exactly one place in the codebase that imports the mcp SDK.

The idea in one sentence: MCPServerBase is the only module that knows the MCP protocol exists. ChunkHoundDaemon, StdioMCPServer, and HttpMCPServer become thin, protocol-version-agnostic wrappers that each supply a transport (IPC frames, stdin/stdout lines, or an ASGI app) and call two inherited methods — serve_connection() and build_streamable_http_app() — without ever importing mcp themselves. ClientProxy was already SDK-free and is unaffected.

1. Why

  • Today: SDK-touching code is scattered across four places — MCPServerBase._register_common_tool_handlers() (tool wiring), StdioMCPServer.run() (builds InitializationOptions/NotificationOptions, opens mcp.server.stdio.stdio_server()), HttpMCPServer.__init__ (builds StreamableHTTPSessionManager directly), and the Option B plan's planned daemon/sdk_session.py (a fourth, daemon-only copy of the per-connection driver). Any future protocol change (a new SDK version, a new era, a new negotiation rule) touches up to four files.
  • With this design: all of that collapses into two methods on MCPServerBase. A protocol-version change is a change to one file. The daemon, stdio, and HTTP wrappers don't change at all unless their own transport plumbing changes.
  • Enforcement, not just convention: a static test parses the AST of each wrapper file and fails the build if any of them import mcp — see §4.

3. Common flows

Flow A — daemon path (default)

  1. Client spawns chunkhound mcp → routes to ClientProxy (SDK-free, unchanged).
  2. ClientProxy discovers/spawns the daemon (DaemonDiscovery), registers over IPC, then relays stdio JSON lines ↔ IPC msgpack frames — exactly as today.
  3. On the daemon side, ChunkHoundDaemon._handle_client() (after the proxy's register/registered handshake) calls the **inherited** self.serve_connection(read_frame=ipc.read_frame, write_frame=ipc.write_frame).
  4. serve_connection() (defined once, in MCPServerBase) builds the SDK stream pair, drives self.server.run(...) for that connection — dual-era negotiation, tools/list/tools/call dispatch — and calls handle_tool_call against the daemon's single DB/provider state.
  5. ChunkHoundDaemon's own source file never imported mcp to make any of this happen.

Flow B — no-daemon / --stdio / read-only

  1. Client spawns chunkhound mcp --no-daemon (or --stdio, or read-only is forced) → routes to StdioMCPServer, which owns its own DB/providers/watcher (no daemon exists to proxy to).
  2. StdioMCPServer.run() builds its own read_frame/write_frame pair — plain stdin/stdout JSON-line read/write, the same framing ClientProxy already uses, just without the IPC hop.
  3. It calls the same **inherited** self.serve_connection(read_frame, write_frame) the daemon uses — identical protocol handling, different transport underneath.
  4. stdio.py's own source file never imports mcp either — it used to (today's mcp.server.stdio.stdio_server(), InitializationOptions, NotificationOptions), and this design moves that out.

Flow C — HTTP

  1. Client connects to the standalone chunkhound mcp --transport http process (never touches the daemon, same as today).
  2. HttpMCPServer calls the **inherited** self.build_streamable_http_app(stateless=False) instead of constructing StreamableHTTPSessionManager itself.
  3. The returned ASGI app is mounted at /mcp behind the existing bearer-auth/CORS Starlette middleware (unchanged — those are not SDK-specific).
  4. http_server.py's own source file never imports mcp either — it used to (from mcp.server.streamable_http_manager import StreamableHTTPSessionManager), and this design moves that out.

What never changes

  • ClientProxy and the IPC wire format (daemon/ipc/codec.py) — untouched by this design, already SDK-free.
  • The shared tool core (mcp_server/common.py, tools.py) — every flow still converges on the same handle_tool_call.
  • The routing rules in api/cli/commands/mcp.py that pick which wrapper runs.
  • No Rust integration anywhere in this design, consistent with the Option B decision.
